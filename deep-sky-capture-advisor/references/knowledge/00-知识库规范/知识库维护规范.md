# 深空天文拍摄知识库维护规范

## 目标

本知识库面向深空天文拍摄爱好者和 AI Agent，目标是让知识同时具备：

- 人可读：使用普通 Markdown，不依赖专有阅读器。
- 机可读：每个概念页具有结构化 YAML frontmatter。
- 可追溯：页面列出来源，正文保留可访问的资料链接。
- 可导航：根目录和每个分类目录都有 `index.md`。
- 可维护：页面显式记录生命周期、时效和审核状态。
- 可积累：新增资料先进入原始资料层，再编译或更新 Wiki 概念页。

## 知识库分层

| 层级 | 位置 | 用途 | 修改规则 |
|---|---|---|---|
| 原始资料层 | `/raw/` | 保存调研材料、摘录和待编译来源 | 正文只追加或另存新版本，不静默覆盖 |
| Wiki 层 | `/01-新人入门/` 至 `/09-踩坑与复盘/` | 面向读者和 Agent 的结构化知识 | 综合来源后更新，必须维护元数据和关联链接 |
| 治理层 | `/00-知识库规范/` | 结构、质量、审核和维护规则 | 变更需记录到根目录 `log.md` |
| 归档层 | `/archive/` | 保存已弃用但仍需维持旧链接的页面 | 页面使用 `status: deprecated` |

## OKF v0.2 最低要求

除 `index.md` 和 `log.md` 外，每个 Markdown 文件必须：

1. 以可解析的 YAML frontmatter 开头。
2. 包含非空 `type`。
3. 推荐包含 `title`、`description`、`tags`、`status`、`generated`、`stale_after` 和 `sources`。

根目录 `index.md` 声明 `okf_version: "0.2"`。子目录 `index.md` 不使用 frontmatter，只列出本目录内容和一句话说明。`log.md` 按 ISO 日期倒序记录变更。

## 页面元数据约定

```yaml
---
type: "Playbook"
title: "极轴校准"
description: "说明极轴校准的目标、方法、验收标准与常见问题。"
category: "03-拍摄SOP"
tags: ["拍摄", "极轴校准", "新手"]
difficulty: "新手"
audience: "使用赤道仪进行长曝光的拍摄者"
status: stable
created: "2025-07-10"
updated: "2026-07-30"
stale_after: "2027-07-30"
generated:
  by: process:okf-migration
  at: "2026-07-30T12:00:00+08:00"
review:
  state: needs-human-review
  owner: knowledge-base-maintainer
sources:
  - id: source-id
    resource: "https://example.com/source"
    title: "来源标题"
applies_to:
  系统: ["与本文结论有关的器材或软件范围"]
  条件: ["会改变结论的观测、数据或运行前提"]
  不适用: ["明确排除的系统或场景"]
---
```

### 生命周期

- `draft`：内容未完成或不可直接采用。
- `stable`：结构完整，可供使用；不等于已经人工核验。
- `deprecated`：已被替代，仅为旧链接和历史保留。
- `stale_after`：到达该日期后必须复核，不应自动视为仍然正确。

### 信任与审核

- 没有 `verified` 的页面均视为未验证。
- 仅在真人逐项对照来源后，才可添加 `verified: { by: human:<id>, at: <ISO-8601>, scope: <已核验范围> }`。
- 自动检查只能记录非 `human:` Actor，不得冒充人工审核。
- 发现冲突时保留双方说法，并使用醒目的“待核验/存在分歧”说明，不静默选择其一。

### 权威问答资格

公开问答中的“权威”是发布资格，不是语言风格。页面只有同时满足以下条件，才能在 `verified.scope` 范围内承担权威回答：

1. `status: stable`，且当前日期未超过 `stale_after`。
2. frontmatter 包含具体、非空的 `applies_to.系统`、`applies_to.条件` 和 `applies_to.不适用`。
3. 会改变采购、运行、处理或安全决定的主张，在正文就近绑定同页 `sources[].id`，并写明版本、条件和失效边界。
4. 来源身份、访问日期、权利状态及关键证据位置已由审核人核对；经验来源不能单独支撑高影响结论。
5. 具名领域审核人完成逐项复核，并写入 `verified: { by: human:<id>, at: <ISO-8601>, scope: <已核验范围> }`。
6. 问答系统实际引用的所有关键页面均满足上述条件；混入任一未审核、过期或超出签署范围的依据时，整条回答只能标为“非权威参考”。

自动构建、链接检查、模型复述、来源可访问或 `stable` 状态均不能替代第 5 项。`verified.scope` 必须描述已核验的主张范围，不允许使用“全文”“全部正确”等无法审计的空泛签署。

## 页面类型

| type | 用途 |
|---|---|
| `Concept` | 解释“是什么、为什么” |
| `Learning Path` | 按阶段组织学习顺序 |
| `Buying Guide` | 器材选型和取舍 |
| `Equipment Reference` | 器材类别、参数与兼容性 |
| `Playbook` | 可执行的现场或拍摄流程 |
| `Method` | 可复用的后期处理方法 |
| `Target Reference` | 目标天体和推荐参数 |
| `Planning Reference` | 选址、天气、月相与窗口 |
| `Software Guide` | 软件配置与操作 |
| `Comparison` | 并列比较多种工具或路线 |
| `FAQ` | 高频问题与短答案 |
| `Troubleshooting Guide` | 故障诊断与复盘 |
| `Research Source` | 原始或汇总调研材料 |
| `Governance` | 知识库规范与维护制度 |

一个页面应解决一个清晰主题。方法页回答“怎么做”，概念页回答“是什么”；内容过长或包含多个可独立复用主题时再拆页。

## 来源与引用

- `sources` 记录页面整体来源；每个条目必须有可访问的 `resource`。
- 具体数值、型号能力、软件行为和时效性结论，应在正文附近使用 `[^sources-id]` 引用；站点将其连接到同页来源卡，自动门禁要求该 ID 存在于 frontmatter 的 `sources[].id`。
- 包含参数、兼容性、软件步骤或安全结论的页面应在 frontmatter 记录 `applies_to`，并在每条关键主张附近说明实际适用的设备、版本、环境/数据前提和不适用范围。具体格式见[主张级引用与适用条件](/00-知识库规范/主张级引用与适用条件.md)。[^claim-condition-policy]
- 优先使用官方文档、原始研究或厂商规格；论坛和个人经验应明确标注为经验性信息。
- 不确定或相互矛盾的内容进入待核验状态，不得被 LLM 自动“调和”成无来源结论。
- `/raw/` 中的来源正文视为不可变输入；对用户明确纳入维护范围的官网资料，先保存带 URL、抓取时间、哈希、采集状态与访问边界的受限文本捕获，再由 Wiki 页面综合多个来源并保留来源链。
- 公开站不直接发布 `/raw/` 正文，只发布必要的追溯摘要与外链；许可未知的外部内容不得镜像、嵌入或大段复制。`/raw/` 的受限文本捕获不构成公开转载授权，必须保持 `content_withheld: true`。详细门禁见[来源许可与发布门禁](/00-知识库规范/来源许可与发布门禁.md)。
- 来源可选记录 `rights`（`permitted`、`restricted`、`unknown`）、`license`、`rights_evidence`、`accessed_at` 与 `usage`。未声明时编译台账一律显示 `unknown`，不得自动推断为已授权；声明 `permitted` 时必须提供权利证据。

## 链接与命名

- 概念页使用稳定的中文文件名，不再把版本号或日期写进文件名。
- 页面间优先使用从知识库根目录开始的绝对链接，例如 `/03-拍摄SOP/极轴校准.md`。
- 每页末尾维护“关联知识”，用于形成可遍历的知识图谱。
- 删除页面前应先改为 `deprecated` 并提供替代页面链接；避免直接造成断链。

## LLM 读写流程

1. 先读根目录 `index.md`，再读目标分类的 `index.md`，按渐进披露定位页面。
2. 回答问题前检查 `status`、`stale_after`、`review.state` 和 `sources`。
3. 新资料先存入 `/raw/`，保留文本型原始捕获、出处、抓取日期、正文哈希与采集失败状态；不下载未获授权的图片、视频、PDF 或附件。
4. 只更新与新资料相关的概念页，避免把资料目录机械复制成 Wiki 目录。
5. 为新的高影响结论补 `applies_to`、就近 `[^source-id]`、来源访问日期、可复核产物和失效条件；输入不足时保留待确认项，不把案例参数泛化。[^claim-condition-policy]
6. 新结论必须合并到既有概念边界中；确有独立主题时才新建页面。
7. 更新 `description`、`updated`、`generated`、`stale_after`、`sources`、关联知识和目录索引。
8. 在根目录 `log.md` 追加变更说明，并运行 OKF、权威资格与链接检查。
9. 未经人工核验，不添加 `human:` 的 `verified`；完成审核时同时记录具体 `scope`，不得只写 Actor 和时间。

## 复核频率

| 内容 | 建议复核周期 |
|---|---|
| 软件版本、器材型号、价格、在线服务 | 3-6 个月 |
| 目标参数、天气工具、远程台信息 | 6 个月 |
| 拍摄 SOP、后期方法、故障排查 | 12 个月 |
| 基础概念与治理规范 | 12 个月或规范升级时 |

## 权威问答口径

- 本页可承担的回答范围：本仓库 Markdown/Git 知识源、维护流程与只读问答派生层；成立条件：页面遵循 OKF v0.2、来源追溯、审核与失效日期约定。
- 遇到以下情况必须拒绝确定结论或转入专项页/实测：把生命周期 stable 解释为人工核验完成；允许外部问答系统反向写回 Wiki。
- 具体数值、兼容性、软件行为或安全结论只使用正文就近绑定的来源，并同时受 `stale_after` 与人工 `verified.scope` 限制。
