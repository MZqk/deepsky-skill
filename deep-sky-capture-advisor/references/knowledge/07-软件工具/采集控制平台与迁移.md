# 采集控制平台选择与迁移

**摘要**：控制平台的选择不是“哪个软件功能更多”，而是“这套设备、驱动、固件和运行方式能否完成并安全恢复关键动作”。ASCOM 的 COM 与 Alpaca 提供设备接口层，INDI 也提供与 Alpaca 的互操作；这些接口不等于任意客户端都已实现全部功能。[^ascom-master-interfaces] [^indi-alpaca-interop]

## 先分清四个层次

| 层次 | 要回答的问题 | 不应推断的结论 |
|---|---|---|
| 设备与固件 | 这台相机、赤道仪、调焦器、滤镜轮和安全设备的型号/固件是否受支持？ | 同品牌或同一接口就一定可用。 |
| 驱动与协议 | 是厂商原生驱动、ASCOM COM、Alpaca、INDI 还是桥接？ | 协议可连通就具备全部设备能力。 |
| 采集客户端 | 能否完成居中、对焦、导星、翻转、停泊、日志与异常处理？ | 软件有一个开关就已完成安全自动化。 |
| 现场运行 | 在真实光路、供电和线缆下是否已通过干跑和测试帧验收？ | 模拟器或白天连接成功就能无人值守。 |

ASCOM 将相机、调焦器、滤镜轮、赤道仪、观测条件与 SafetyMonitor 等定义为接口；这些定义刻意独立于操作系统和具体设备。[^ascom-master-interfaces] INDI 的 Alpaca 互操作被标为 preliminary，因此桥接设备要额外记录驱动版本和实际测试范围。[^indi-alpaca-interop]

## 平台能力矩阵：先写“已验证”，再写“支持”

下表用于选择路线与提出问题，不是型号兼容白名单。每个格子都应回到厂商当前的支持页、设备手册和自己的干跑记录。

| 路线 | 适合的控制方式 | 迁移时要保留 | 首次自动化前必须验证 |
|---|---|---|---|
| Windows + N.I.N.A + ASCOM | 希望用 Windows 设备驱动、板解、对焦、导星和高级序列构建可编辑流程的系统。[^nina-manual] | N.I.N.A 配置/模板、ASCOM 驱动版本、插件版本、PHD2 profile 与日志目录。 | 设备连接、居中、自动对焦、导星、翻转、停泊及故障后的日志定位。 |
| ASIAIR | 希望用厂商控制器和移动端完成已在官方清单内的设备组合。访问日的软件页列出 V3.0 与 2026-07-29 发布日期。[^asiair-software] | 应用/固件版本、设备支持清单快照、导出方式、原始子帧和日志位置。 | 当前型号和移动端系统是否受支持；远程网络、重启、导出、停泊与翻转是否在本机实际可用。 |
| KStars/Ekos + INDI | 希望在 INDI 生态中管理设备、序列、规划、对焦、导星和调度的系统。[^ekos-manual] | INDI profile、驱动版本、设备 XML/配置、日志与调度文件。 | 远程 INDI 服务、位置/时间同步、板解、停泊/限位、翻转和安全设备状态。 |
| 厂商软件或手动流程 | 设备尚未被目标平台支持，或先以最小链路验证硬件。 | 安装包、固件版本、厂商手册、已知可用的连接顺序和原始文件导出办法。 | 原始数据可保存、设备可安全停机；不得因为“暂时能拍”跳过兼容性记录。 |

把“原生支持”“通过桥接可用”“只验证连接”“未验证”“不支持”分开写。尤其不要把 ASCOM/INDI/Alpaca 名称或品牌名称当作设备能力证明。[^p0-source-record]

## 建立一张可迁移的系统卡

每套实际可运行系统保存一份配置快照；复制或升级前先复制这份卡，而不是仅记住应用名称。

```yaml
system_id: "my-rig-2026-08"
verified_at: "2026-08-13"
control:
  platform: "N.I.N.A / ASIAIR / Ekos / 厂商软件"
  app_version: "实际版本"
  host_os_and_model: "Windows / Linux / 控制器型号"
devices:
  mount: "型号 + 固件 + 驱动/协议"
  camera: "型号 + SDK/驱动 + 读出模式"
  focuser_filter_guider: "型号 + 固件 + 驱动"
support_level:
  connect: "已验证 / 未验证"
  center_focus_guide: "逐项填写"
  flip_park_safety: "逐项填写"
artifacts:
  config_export: "路径或导出日期"
  logs: "应用、导星和系统日志位置"
  raw_data_export: "原始子帧与 FITS 头检查结果"
rollback:
  known_good_versions: "应用、驱动、固件"
  restore_steps: "恢复顺序与白天复验项目"
```

地点、序列号、局域网地址、账号和令牌不要写入公开页面或共享模板；它们属于需要单独保护的运行信息。

## 更新、迁移与回滚流程

1. **冻结已知可用状态**：导出配置或截图，记录应用、驱动、固件、插件、设备连接与日志位置；把原始子帧和关键测试帧留在可回退目录。[^p0-source-record]
2. **只改变一个层次**：优先单独更新应用、驱动或一个设备固件；不要在同一晴夜同时替换控制器、镜组和全部软件。
3. **白天做最小回归**：在真实光路与线缆下逐项验证相机采集、滤镜、调焦、赤道仪运动、板解、导星连接、停泊与翻转运动包络。
4. **首夜有人在场**：先拍短测试序列并保存日志；翻转、对焦或设备重连失败时停止扩展自动化范围。
5. **回滚而非猜测**：若失败发生在变更后，恢复到已知可用版本和配置，再以单一变量重测；不要在黑暗中临时混用不明驱动或论坛文件。

ASIAIR 的软件页说明应用与固件都会更新；这类更新必须按“版本快照—回归—首夜在场”处理，而不是根据应用商店提示直接在拍摄前安装。[^asiair-software]

## 迁移验收：连接成功不等于可安全自动化

| 验收项 | 可接受证据 | 未通过时的边界 |
|---|---|---|
| 原始数据 | 可打开的原始子帧、FITS 头/文件名、导出路径与存储空间记录。 | 先回到手动采集或厂商软件，不能开始多夜计划。 |
| 设备链路 | 每台设备的型号、驱动、固件、端口与重连行为已记录。 | 不把未验证设备放进无人值守序列。 |
| 关键工作流 | 居中、自动对焦、导星、抖动、翻转、停泊分别在真实系统通过。 | 只可在场使用已通过的子集。 |
| 安全与恢复 | 线缆包络、限位、停机动作、日志与远程/本地人工接管已演练。 | 禁止以天气触发或软件定时器代替硬件和人工安全边界。 |

## 权威问答口径

- 本页可承担的回答范围：使用赤道仪、相机、调焦器、滤镜轮或导星设备的深空采集系统；成立条件：迁移前后保存版本与设备矩阵，并以真实镜组完成连接、运动、停泊和回滚干跑。
- 遇到以下情况必须拒绝确定结论或转入专项页/实测：只有手动三脚架且不使用设备控制软件的单张拍摄；未核对厂商兼容列表的具体型号推荐。
- 具体数值、兼容性、软件行为或安全结论只使用正文就近绑定的来源，并同时受 `stale_after` 与人工 `verified.scope` 限制。
